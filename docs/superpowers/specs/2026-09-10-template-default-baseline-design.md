# 范本默认值基线 + 变化字段确认填写 设计

- 日期：2026-09-10
- 状态：设计已确认（待实施）
- 关联：`2026-09-07-template-fill-design.md`（模板填写系统）、`2026-09-08-template-fill-flow-design.md`（进度流式）、`2026-09-09-template-fill-cancel-retrieval-design.md`（取消链路）

## 1. 背景与痛点

范本多为 90 页左右、占位符几百个：

1. **空范本首填**：几百个 llm 字段全量走检索+LLM 产值（batch=10 → 几十次调用），慢、贵、部分字段提取不到。
2. **重复填写**：填过一次的范本，大部分内容每次不变，实际只需改 ~100 个字段——但现状每次仍全量重跑。

核心洞察：`TplFillTask.values` 已经存了每次产值，只是没有回填利用；识别器做「值→占位符」替换时天然知道已填范本的现值，也被丢弃了。

## 2. 方案总览

给占位符引入「默认值」存储，三个来源沉淀、一次确认、条件执行：

- 重填时：有默认值且未被判定为变化的字段**直接复用，不检索不调 LLM**；
- 只对「变化字段」走 LLM 产值，且默认值注入 prompt 作参考；
- LLM 提取不到时 fallback 默认值，根治漏填。

收益估算（400 默认字段 / 100 变化字段）：LLM 产值调用从 ~40 批次降到 ~10+1 次（+1 次预判），检索量降约 75%。

## 3. 数据模型

`TplTemplateVersion.placeholders` 每个占位符 item 新增两个字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `default_value` | str | 默认值，空串 = 无 |
| `default_source` | str | `detected`（识别提取）/ `auto`（填写沉淀）/ `manual`（B端手动）/ `""`（无） |

- 不加新表：符合「占位符清单随版本原子演进」的既有设计；字段级编辑 = 整体更新 placeholders，几百字段 JSON 单次写入无压力。
- 旧数据无这两个字段 = 无默认值，天然兼容。
- 版本重新识别：按 key 匹配继承旧默认值，新 key 从空开始。

## 4. 默认值的三个来源

| 来源 | 时机 | 机制 |
|---|---|---|
| `detected` | 上传已填范本、AI 识别时 | 识别器做「值→占位符」替换时顺带落库。xlsx 按 addr 直读单元格（零 LLM 成本）；docx 由识别 LLM 顺带提取现值 |
| `auto` | 每次填写成功后 | 本次 LLM 产值 + 用户直填值自动写回 `default_value`（source=auto）；**不覆盖 manual** |
| `manual` | B端范本库编辑 | 范本详情新增「默认值」页签：字段列表（名称/默认值/来源/更新时间），支持搜索、逐个编辑/清空 |

## 5. 填写流程（核心变化）

```
选范本 → 占位符分两组：
  D = 有默认值的字段
  N = 无默认值字段（照旧检索 + LLM）
→ ① 预判：1 次轻量 LLM 调用，输入 = 需求描述 + D 字段清单（key/name/默认值摘要），
       输出 = 疑似变化字段集合 C
→ ② 暂停确认：推 SSE confirm_pending 事件（C 清单 + 默认值展示），节点挂起等待
     用户可：勾掉预判误判 / 追加字段 / 直接给值（跳过 LLM）
     超时 10 分钟 → 按预判结果自动继续
     预判 LLM 失败 → C = ∅（全部保持默认，用户确认时手动挑）
→ ③ 条件执行：
     用户直填值 → 直取
     C ∩ D     → 检索 + LLM 产值（默认值注入 prompt 作参考）
     D − C     → 直接用默认值，不检索不调 LLM
     N         → 照旧检索 + LLM
→ ④ 渲染成稿 → 自动沉淀（按 §4 规则）
```

- 首填场景（无任何默认值）：跳过预判与确认，行为与现状完全一致。
- 沉淀写库失败：仅记日志告警，不影响成稿交付。
- manual 保护：B端手动改的值不被 auto 沉淀覆盖；用户在确认卡片显式给的值总是覆盖。

## 6. 暂停/唤醒机制

复用 2026-09-09 取消链路的模式：

- Redis key：`tpl_fill:confirm:{task_id}`，节点侧 1~2s 轮询（与 should_cancel 探针同款）。
- 新端点：`POST /template-fill/confirm`，body：`{task_id, changed_keys, values}`；写 Redis 后节点继续。
- 前端：C端对话与 flow AI 面板共用 SSE 进度事件管道（FanOut/TemplateFill 同款），新增 `confirm_pending` 事件类型，收到后就地渲染确认卡片；提交调 confirm 端点。
- 用户关闭页面未提交：走超时自动继续。

## 7. 边界与对抗性考量

| 场景 | 处理 |
|---|---|
| 预判 LLM 超时/失败/返回非法 JSON | C=∅，确认卡片提示「预判失败」，用户手动挑选变化字段 |
| 用户 10 分钟未确认 | 按预判结果自动继续，进度事件注明 |
| 确认 values 中含不存在的 key | 过滤忽略，记日志 |
| 用户直填值为空串 | 视为「清空该字段」而非跳过，渲染为空 |
| 沉淀与 B端编辑并发 | 以占位符整体 JSON 为写入单元，后写覆盖；B端编辑页提交前刷新数据 |
| 重新识别后 key 集合变化 | 按 key 匹配继承，孤儿默认值随旧版本自然废弃 |
| 首填 LLM 大面积失败 | 现状行为不变（缺失字段留空），用户可在 B端默认值页手动补录，下次生效 |

## 8. 实施拆分

- **P1（独立可交付，根治漏填 + 数据就绪）**：
  数据模型字段 + 识别提取现值（detected）+ 填写后自动沉淀（auto）+ B端「默认值」编辑页 + LLM 提取不到时 fallback 默认值。
- **P2（降本提速）**：
  变化字段预判 + 对话中暂停确认（confirm_pending SSE 事件 / confirm 端点 / 前端确认卡片，C端对话 + flow AI 面板）+ 条件执行（D−C 免检索免 LLM）。

## 9. 测试要点（对抗性）

- 默认值继承：同 key 跨版本继承、key 消失/新增、manual 不被 auto 覆盖、确认直填覆盖 manual。
- 预判对抗：需求描述为空/超长、D 为空、D 全量超大清单截断、LLM 返回非法 JSON/编造 key。
- 暂停确认：超时、用户重复提交 confirm、confirm 的 task_id 不存在/已结束、SSE 断线重连后卡片状态。
- 沉淀：写库失败不影响成稿、几百字段大 JSON 写入、并发两次填写同一范本的沉淀竞态。
- xlsx addr 直读现值：合并单元格、空单元格、格式化数值（日期/金额格式）。
