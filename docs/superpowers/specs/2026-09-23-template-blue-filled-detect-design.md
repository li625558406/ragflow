# 范本识别：蓝色已填值识别为填写点+默认值（docx）设计

日期：2026-09-23
状态：设计已获用户确认

## 1. 背景与问题

B端范本库现有 AI 识别（`detect_fill_points`）是**纯文本层面**的：
`blank_slots.py` 在 run 层按格式切位（下划线/连续空白/括号提示），LLM 只标注语义。
docx XML 中 run 的颜色信息（`w:color`）从未被利用。

一类真实上传文件：占位符位置**已用蓝色字体填了旧值**（蓝色≈已填值标记，用户确认这类
文件里蓝色基本没有其他用途）。现状下：

- 蓝色实心文字**不是留白**，blank_slots 切不出位（「下划线空位被填了蓝字」形态整簇
  分类失败、逐 run 回退也判空）→ 该行退化为 V1 LLM 自选 anchor，识别质量差且
  **不产默认值**（V2 硬闸 + V1 依赖 anchor 形态）；
- 用户需要：蓝色旧值被识别为**填写点**，旧值沉淀为该点 **default_value**，
  下次为新项目填写时与其他填写点一样由 AI 换新值，检索不到时默认值兜底。

## 2. 需求结论（澄清记录）

| 问题 | 结论 |
|------|------|
| 蓝色值用途 | 作为该填写位置的默认值（下次填写 AI 换新值，同其他填写点） |
| 文件类型范围 | 仅 docx（xlsx 提取无 slots 通道，天然不涉及） |
| 蓝色纯度 | 蓝色≈已填值标记（无蓝色标题/超链接等干扰），仍保留人工确认兜底 |

## 3. 方案选型

**方案 A（采纳）：扩展 V2 管线，蓝色 run 作为新 slot 类型（kind="blue"）。**
复用全部既有链路（合并/occ 校验/人工确认/渲染替换/默认值消费），改动集中在
`blank_slots.py` + `detector.py` 两个文件。

落选：
- 方案 B（detect 后独立扫蓝色 run 追加候选）：两套坐标系两条链路，与 V2 项在同段
  混合行上撞车处理复杂。
- 方案 C（上传时把蓝色文本改写为 {{key}} 占位符直通）：需改写原文件、key 语义缺失、
  与 detect 产物融合别扭。

## 4. 设计

### 4.1 识别层：蓝色切位（`blank_slots.py`）

**蓝色判定 `_is_blue_run`**：
- 输入 run 的 `font.color.rgb`（hex RGB），判据 = **B 通道严格占优**：
  `B - max(R, G) >= 40`。
- 覆盖常见蓝：0000FF（255-0）、0070C0（192-112=80）、4472C4（196-114=82）、
  1F4E79（121-78=43）、2E74B5（181-116=65）；排除黑/灰（差值 0）、红、绿。
- 仅认 rgb 直值；`color.type` 为主题色且 rgb 为 None 时保守跳过（宁漏不误）。
- **run 文本必须含非空白字符**——蓝色格式打在空白上不算已填值。

**切位规则**（`extract_paragraph_slots` 主扫描循环，blue 优先级高于下划线）：
- 连续蓝色 run 成簇（一个值常被 Word 拆成多 run），簇文本 = slot，
  `kind="blue"`，`hint=""`。
- 相邻 blue 段之间只隔空白 → 合并为一个值段（复用既有 gap_blank 合并语义）。
- **blue 优先**：蓝色且含实心文字的 run 归 blue 簇，不再进下划线簇判定——
  天然覆盖「下划线空位被填了蓝字」形态（现状该形态切不出位只能走 V1，本次顺带补齐）。
- 蓝色空白文本的下划线 run（空位未填）→ 仍走既有 blank/hint 逻辑。
- 同受 `_MAX_SLOT_LEN=500` 封顶；含 `w:hyperlink` 段落维持整段不切位
  （runs 坐标系不可靠，既有约束不变）。

### 4.2 语义标注与默认值派生（`detector.py`）

- **`DETECT_SYSTEM_V2` prompt** 增补：位文本可能已是填好的旧值（蓝色已填位），
  照常标注字段语义。
- **`parse_slot_response`**：`slot.get("kind") == "blue"` 时
  `default_value = slot["text"]`（旧值即默认值，来源=detected）；其余位维持
  `default_value=""` 硬闸不变。豁免依据：当年硬闸理由是「切出的留白无值可派生」
  （2026-09-12 设计 §4.5），blue 位文本本身就是值，性质不同。
- **`slot_fallback_items`**：LLM 漏标的 blue 位兜底成点：
  `name="已填填写点"`、`low_confidence=True`、`default_value=位文本`
  （值是确定性的，不因 LLM 漏标丢失；低置信只针对机器生成的语义命名）。
- key/name/retrieval_query 走既有 LLM 标注 + `normalize_key` + 去重后缀链路，
  零新逻辑。slot 文本必须仍是候选原文子串的防御校验对 blue 位同样生效。

### 4.3 下游链路（零改动，自然生效）

- **B端确认列表**：blue 位作为普通填写点行出现，默认值列回显旧值
  （09-17「B端模板预览回显默认值」既有功能）。
- **渲染**：anchor=旧值文本 → `{{key}}` → 成稿中新值继承蓝色 run 格式
  （成稿标蓝，与系统既有惯例一致）。
- **填写消费链**：`default_map` → 确认卡 → baseline → 全部既有，零改动。
- **存量范本**：需在详情页重新识别才生效；无数据迁移。
- **前端**：零改动。

## 5. 边界与限制（诚实声明）

1. 样式级颜色继承（蓝色定义在 Word 样式而非 run rPr）抓不到 → 该值漏识别，
   人工可手动添加填写点兜底。
2. 同一行两个独立蓝色值只隔一个空格 → 合并为一个位（默认值为拼接串），
   人工确认环节可改。
3. 蓝色判定是启发式（阈值 40）：蓝紫系（如 8080FF，B-R=127）会命中，属可接受
   误报方向；偏灰蓝可能漏，漏报方向由人工确认兜底。
4. 仅主题色无 rgb 直值的 run 漏识别。

## 6. 测试

- `blank_slots` 单测：纯蓝值多 run 拆分成簇；蓝+下划线混合（已填蓝字的下划线位）；
  蓝色空白文本不切位；黑字/红字不切；相邻 blue 段空白合并；500 封顶；
  hyperlink 段落跳过；themeColor-only 跳过。
- `detector` 单测：blue 位 `default_value` 派生；其余位硬闸不回归（回归闸）；
  fallback 兜底 blue 位带默认值+低置信；blue 位 slot 文本腐坏防御丢弃。
- 对抗：空 slot 文本、超长蓝值（>500）、RGB 相等色、`kind` 字段缺失/畸形、
  LLM 对 blue 位漏标。
